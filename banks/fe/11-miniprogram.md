# 模块 11：小程序

### Q11.84【高·高频·概念】微信小程序为什么采用「双线程架构」（视图层和逻辑层分离）？这种架构有什么优缺点？

**考察点:** 双线程：视图层（WebView 渲染）和逻辑层（JSCore 跑 JS）分离，通过 Native 桥通信。目的是安全和可控——逻辑层拿不到 DOM，防止开发者操作 DOM 跳转/改 UI，便于微信管控；同时多页面复用 WebView。代价是通信有延迟、不能用 DOM API。

**参考答案要点:**
**双线程架构**：
- **视图层（WebView）**：每个页面一个 WebView，负责渲染 WXML/WXSS。可以有多个（多页面）。
- **逻辑层（JSCore/V8）**：只有一个，跑所有 JS 逻辑（数据、事件处理）。**没有 DOM/BOM API**。
- **Native 层（微信客户端）**：作为中间人，在两个线程间转发数据和事件。

**示例:**
**双线程通信流程**：
```
用户点击按钮
  → 视图层(WebView) 捕获事件
  → 经 Native 转发到 逻辑层(JSCore)
  → 逻辑层处理，调用 setData
  → setData 数据经 Native 回到 视图层
  → 视图层重新渲染
```

### Q11.85【高·高频·概念】小程序的 WXML/WXSS 最终编译成什么？为什么不能直接用 HTML/CSS？

**考察点:** WXML 编译成 JS（通过 WCC 编译器转成 render 函数生成虚拟 DOM），不是直接转 HTML；WXSS 编译成 JS 注入的样式。因为双线程架构下视图层要动态生成、要适配多端、要做安全管控（不能让开发者写任意 HTML/JS 操作 DOM），所以用自定义标签再编译。

**参考答案要点:**
**WXML 的编译产物**：
- WXML 不是直接转成 HTML。它经过 **WCC 编译器**，编译成一个 JS 函数（$gwx）。
- 运行时，逻辑层把数据传给这个函数，函数生成**虚拟 DOM 树（JS 对象）**。
- 虚拟 DOM 树再通过 setData 传到视图层，渲染成实际的渲染层节点（基于 WebView 但做了封装）。

**示例:**
**编译流程**：
```
开发：写 WXML (<view>{{msg}}</view>)
  ↓ 编译时（WCC）
生成：$gwx render 函数（JS）
  ↓ 运行时
逻辑层：$gwx({msg:'hi'}) → 生成 vnode {tag:'view', children:['hi']}
  ↓ setData
视图层：渲染成 <view>hi</view>
```
