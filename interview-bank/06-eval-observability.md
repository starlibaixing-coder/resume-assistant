# 模块 06：评测 & 可观测性

> **优先级：🔥 必问**　**覆盖 JD：JD1/2（明确要求效果评估体系、全链路可观测、Bad Case 归集）**
> 这是 JD1/2 的核心职责。区别于模块 10 的「整体工程化」，本模块聚焦于**评测方法论**和**可观测性技术栈**本身。

```
评测（离线/在线）  ←→  可观测性（trace/metrics/log）  ←→  迭代闭环
```

## 题目

### Q06.1【高·必问】设计一个 Agent 的评测体系，包含哪些维度和指标？

**考察点：** 评测方法论是否系统、指标是否对齐业务目标。

**参考答案要点：**
- **能力维度（不止一个）**：
  - 任务完成度：任务成功率、完成耗时、步骤数；
  - 正确性：答案准确率、faithfulness（是否忠实检索内容）；
  - 工具使用：工具调用准确率、参数正确率、冗余调用数；
  - 效率：Token 消耗、延迟、成本；
  - 体验：人工满意度、重试率、转人工率。
- **指标要分场景**：客服 Agent 看解决率，编码 Agent 看 pass@k，分析 Agent 看数据准确率。
- **基线对比**：每次迭代都要和 baseline 对比，量化提升。
- **关键认知**：单一指标会骗人，必须多维交叉（如成功率高但成本飙升）。

### Q06.2【高】LLM-as-Judge 怎么用才可信？有哪些坑？

**考察点：** 自动化评测的实践经验——这是最容易翻车的地方。

**参考答案要点：**
- **优点**：规模可扩展、成本低、能评开放式问题（无标准答案的）。
- **坑（必须答出）**：
  - **Position bias**：倾向第一个选项 → 交换顺序再判一次取平均；
  - **Self-preference bias**：模型偏好同族模型生成的答案；
  - **Verbosity bias**：倾向更长的答案；
  - **Rubric 不清晰**：评分标准模糊 → 给明确 rubric（分维度打分）+ 参考范例；
  - **校准问题**：和人工不一致 → 先用人工标注校准 judge 模型。
- **最佳实践**：
  - 用强模型做 judge（如 GPT-4 / Claude Opus）；
  - pairwise 比较优于绝对打分；
  - 关键 case 仍要人工抽检；
  - 计算 judge 与人工的一致性（如 Cohen's Kappa）。

**追问方向：** pairwise 比较如何避免 position bias？（随机化顺序、双向各判一次）

### Q06.3【中高】你怎么为一个新 Agent 建立第一批评测集（golden set）？

**考察点：** 评测集构建的实战方法。

**参考答案要点：**
- **来源**：
  - 真实用户 query 采样（最有代表性，但要脱敏）；
  - 业务专家构造典型场景；
  - 历史 bad case（防止回归）。
- **覆盖**：
  - 覆盖核心意图 / 功能；
  - 覆盖难度梯度（简单 / 中 / 难）；
  - 覆盖边界 case（空输入、多意图、歧义、超长、对抗）。
- **标注**：每条标注理想答案 + 关键步骤 + 验收标准（可校验的）。
- **规模**：起步 50~200 条精标，持续扩充。
- **版本化**：评测集也要版本管理，迭代时增量补充。

### Q06.4【高·必问】Agent 的可观测性要采什么数据？怎么采？

**考察点：** 全链路 trace 的落地细节。

**参考答案要点：**
- **每步要采**：
  - 输入：完整 prompt（含 system / history / retrieved context）；
  - 输出：模型响应、工具调用、参数；
  - 元信息：模型版本、参数（temperature/top_p）、耗时、token（in/out）、成本；
  - 状态：当前步骤、累计步骤、是否完成。
- **会话级串联**：用 session_id / trace_id 串起完整链路。
- **采集方式**：
  - 框架内置（LangSmith / Langfuse 集成）；
  - 装饰器 / 中间件无侵入采集（见模块 11 装饰器模式）；
  - OpenTelemetry 标准化（跨语言、跨后端）。
- **存储与成本**：
  - 全量采成本高 → 采样策略（正常采样 + 异常全量 + 慢请求全采）；
  - 数据脱敏（PII）。

**追问方向：** 如何在不改业务代码的前提下接入 trace？（装饰器 / SDK 自动埋点 / proxy）

### Q06.5【中】Prompt 要不要版本管理？怎么管理？

**考察点：** Prompt 工程化意识。

**参考答案要点：**
- **必须版本管理**：Prompt 是 Agent 的"代码"，改动影响巨大。
- **管理方式**：
  - Prompt 模板独立于代码，存配置 / 文件 / 平台；
  - 版本号、变更说明、作者、关联评测分数；
  - 支持回滚；
  - 环境隔离（dev/staging/prod 用不同版本）。
- **配合评测**：每次改 Prompt → 跑回归 → 记录分数变化 → 通过才发布。
- **工具**：Langfuse Prompt Management、自建平台。

### Q06.6【高】什么是 Bad Case 自动归集？怎么落地？

**考察点：** JD2 明确要求的工程能力。

**参考答案要点：**
- **触发条件**：
  - 用户显式反馈（踩 / 投诉）；
  - 隐式信号（重试、放弃、转人工、长时间无操作）；
  - 系统信号（异常退出、超时、工具失败、faithfulness 低分）。
- **自动归集**：
  - 触发后自动抓取完整 trace（含上下文）；
  - 入库标注（待分析 / 已归因 / 已修复）。
- **分析**：
  - LLM-as-Judge 自动归因分类（规划错 / 检索错 / 工具错 / Prompt 错 / 知识缺失）；
  - 人工复核疑难 case。
- **回流**：归因后进入评测集 / 优化 Prompt / 补知识（数据飞轮，见 Q10.9）。

### Q06.7【中高】JD2 提到的「噪声注入」是什么？用来干什么？

**考察点：** 鲁棒性测试方法（直接对应 JD2）。

**参考答案要点：**
- **目的**：测试 Agent 在输入扰动下的鲁棒性，主动暴露脆弱 case。
- **方法**：
  - 输入扰动：错别字、口语化、多余的指令、无关信息；
  - 上下文扰动：插入无关检索内容（测是否被误导）；
  - 对抗扰动：注入诱导性内容（测 Prompt 注入防御）。
- **评估**：看 Agent 在扰动下是否仍能正确完成任务，找出崩溃边界。
- **价值**：比正常 case 更能暴露问题，是提升鲁棒性的关键手段。
