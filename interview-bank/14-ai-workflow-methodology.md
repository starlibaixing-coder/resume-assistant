# 模块 14:AI 工作流与方法论

> **优先级:🔥 必问**　**覆盖 JD:JD1(明确要求 SDD/Harness)/ JD4 / 全员(重度使用 AI 工具)**
> 这是 JD1 的独家考点,也是判断"是否真懂 AI 时代研发范式"的关键。会用工具 ≠ 懂方法论;**懂方法论的人能放大 10 倍产出**。

## 知识地图:AI 时代的研发方法论栈

```
第 1 层:基础使用
   └─ Chat / 补全 / 直接对话
第 2 层:Context 工程
   └─ 精准喂上下文(@file / 规则文件 / 文档)
第 3 层:Spec-Driven Development (SDD)
   └─ 先写 Spec,再让 AI 按 spec 实现
第 4 层:Agentic Coding
   └─ AI 自主执行(Agentic Loop / Plan-Act-Observe)
第 5 层:可编排的工程体系
   ├─ Skills (可复用的能力封装)
   ├─ Subagent (并行/专业化派发)
   ├─ Plan 模式 / Todo (任务管理)
   └─ Harness (让 AI 在受控框架内闭环)
```

## 第一部分:核心方法论

### Q14.1【高·JD1 必问】什么是 SDD(Spec-Driven Development)?和传统开发有什么区别?

**考察点:** JD1 明确要求"SDD 完整项目经验",必须能讲透。

**参考答案要点:**
- **核心思想**:**先写清楚的规格(Spec),再让 AI 按 spec 实现**,而不是直接让 AI"帮我写个登录功能"。
- **传统开发 vs SDD**:

| 维度 | 传统开发 | SDD |
|---|---|---|
| 起点 | 想到哪写到哪 | 先写 Spec(需求/接口/验收标准/边界) |
| AI 用法 | 当补全工具 | 当按 spec 执行的实现者 |
| 返工率 | 高(边写边发现需求不清) | 低(前置澄清) |
| 可维护性 | 文档滞后 | Spec 即文档 |
| 可控性 | AI 自由发挥易跑偏 | 有明确目标,输出可控 |

- **SDD 流程**:
  1. **需求澄清**:把模糊需求变成明确的 Spec;
  2. **写 Spec**:功能描述、接口定义、数据结构、验收标准、边界 case、非功能需求;
  3. **AI 生成**:按 spec 出计划 → 分步实现(或直接实现);
  4. **Review**:人对照 spec 验收(类似 code review);
  5. **测试驱动**:用 spec 的验收标准做测试,验证实现。
- **为什么 SDD 在 AI 时代更重要**:
  - AI 让"实现"变便宜,**"想清楚要什么"成了瓶颈**;
  - Spec 是人和 AI 的"契约",大幅提升输出可控性;
  - 前置澄清成本 << 返工成本。
- **价值**:把"模糊需求 → 可用代码"的转化率大幅提升,这是 AI 提效的核心方法论。

**追问方向:** Spec 要写到多细?(够 AI 理解即可,不必逐行;关键是接口/边界/验收标准)

### Q14.2【中】什么是 Agentic Coding?和普通的 AI 补全有什么区别?

**考察点:** 理解"Agent 式编码"的范式。

**参考答案要点:**
- **普通 AI 补全/Chat**:
  - 人主导每一步,AI 只在"被问到"时回答/生成片段;
  - 单轮、被动、无状态。
- **Agentic Coding**:
  - 给 AI 一个目标,AI **自主规划 + 执行 + 验证 + 迭代**;
  - 多轮、主动、有状态、能调工具(读写文件/跑命令/测试);
  - 形成 **Agentic Loop**:Plan → Act → Observe → Reflect → 继续。
- **区别本质**:
  - 补全是"人用 AI 写代码";
  - Agentic 是"AI 自己完成代码,人监督把关"。
- **代表**:Claude Code、Cursor Agent 模式、Devin、Aider。
- **价值**:从"增强个人"升级到"派发任务给 AI 同事",处理多文件、多步骤的复杂任务。
- **代价**:可控性下降、成本上升、需要 review 机制。

### Q14.3【高·必问】什么是 Skills?为什么需要它?

**考察点:** AI 工作流的可复用性设计(JD1 相关)。

**参考答案要点:**
- **问题背景**:每次让 AI 做同类任务都要重新解释流程、规则、注意事项 → 重复、易不一致、易遗漏。
- **Skills(技能)的本质**:**把"做某类任务的 Know-How"封装成可复用的能力包**。
  - 通常是一个结构化的指令文件(SKILL.md / prompt 模板),包含:
    - 触发条件(什么时候用这个技能);
    - 执行流程(分步骤的 SOP);
    - 规则与约束(注意事项、边界);
    - 示例(few-shot);
    - 引用资源(脚本/模板/文档)。
- **价值**:
  - **复用**:同类任务一次封装,反复使用;
  - **一致性**:每次执行流程一致,质量稳定;
  - **可积累**:把团队/个人的最佳实践沉淀成技能库;
  - **可分享**:技能可在团队/社区流通。
- **类比**:Skills = AI 时代的"函数/库/工具" —— 把重复逻辑封装复用。
- **实例**:本简历项目就是一个 skill;代码评审、部署、测试生成、文档生成都可封装成 skill。

**追问方向:** Skill 和普通 prompt 模板的区别?(Skill 有触发逻辑、有结构化 SOP、可调用工具、可组合)

### Q14.4【高·必问】什么是 Subagent(子 Agent)?为什么要用它?

**考察点:** 多 Agent 编排在工作流中的应用。

**参考答案要点:**
- **Subagent**:主 Agent 把子任务**派发给独立的子 Agent** 执行,子 Agent 有独立的 context、工具、目标,完成后汇报结果。
- **为什么要用**:
  - **上下文隔离(核心)**:子任务在独立 context 中执行,**不污染主 Agent 的上下文**,避免主 context 爆炸/干扰;
  - **专业化**:不同子 Agent 用不同 system prompt/工具,各司其职;
  - **并行**:多个无依赖子任务并行执行,提速;
  - **token 经济**:子 Agent 只返回摘要/结果,不把全部中间过程塞回主 context。
- **典型场景**:
  - 主 Agent 派"调研 X 技术"给子 Agent,子 Agent 搜索完只返回结论;
  - 大重构:主 Agent 拆分,每个子 Agent 改一个模块;
  - 代码评审:派子 Agent 分别查安全、性能、风格。
- **与多 Agent 协作的关系**:Subagent 是多 Agent 的一种具体落地(supervisor 模式,见模块 01/04)。
- **关键认知**:Subagent 的最大价值是**上下文管理**,而非"分工"本身。

### Q14.5【高】什么是 Plan 模式 / Todo 机制?解决什么问题?

**考察点:** 任务管理在 Agentic 工作流中的作用。

**参考答案要点:**
- **问题**:Agentic Agent 直接开干容易跑偏、丢失目标、步骤混乱、无法追踪进度。
- **Plan 模式 / Todo 机制**:
  - **先规划再执行**:把任务拆成有序的步骤列表(Todo);
  - **逐步推进**:每完成一步打勾,清晰反映进度;
  - **对照检查**:执行中随时对照计划,避免遗漏/跑偏;
  - **动态调整**:发现计划不对可重规划。
- **价值**:
  - 提升复杂任务的**完成度**(不漏步骤);
  - 提升**可控性/可观测性**(进度可见);
  - 模拟人类的工程化思维(先计划再执行)。
- **本质**:把"Plan-and-Execute"模式(模块 01)应用到开发工作流。
- **实例**:Claude Code 的 TodoWrite、Cursor 的 plan 模式、各类 Agent 框架的任务列表。

### Q14.6【高·JD1 必问】什么是 Harness?为什么需要它?

**考察点:** JD1 明确要求"Harness 完整项目经验",必须答得出。

**参考答案要点:**
- **Harness 字面意思**:驾驭工具/束具 —— 引申为**让 AI 在受控框架内自主完成任务的工程体系**。
- **核心定义**:一套**脚手架/工程框架**,让 AI 能在明确边界、工具、流程内**自主闭环**完成开发任务(spec → 实现 → 测试 → 修复 → 交付),而非散漫地对话。
- **Harness 的关键组成**:
  - **工具集**:文件操作、执行命令、测试、git、部署;
  - **流程编排**:SDD 流程、Plan-Todo、Agentic Loop;
  - **环境**:沙箱、依赖、运行环境;
  - **约束与安全**:权限、HITL、审计;
  - **验证机制**:自动测试、lint、对照 spec 验收;
  - **可恢复**:checkpoint、状态持久化。
- **为什么需要**:
  - **裸 Agent 不可靠**:直接对话式 AI 易跑偏、难复现、无保障;
  - **Harness 提供确定性边界**:AI 在框架内自主,但行为可控、可验证、可恢复;
  - **让"AI 自主开发"从 demo 走向生产**。
- **类比**:Harness 之于 AI = 框架之于程序员 —— 不用从零搭,在结构内高效产出。
- **与 SDD 的关系**:SDD 是方法论(怎么想),Harness 是工程实现(怎么做);SDD + Harness = 完整的 AI 工程化开发体系。

**追问方向:** 你搭过什么样的 Harness?(结合项目讲:工具链 + 流程 + 验证 + 环境)

## 第二部分:工作流实战

### Q14.7【高·必问】讲一个你用 AI 完成复杂任务的工作流(从需求到交付)。

**考察点:** 是否有完整的 AI 工程化工作流(行为面 + 方法论综合)。

**参考答案要点(答题框架):**
讲一个**真实、完整闭环**,体现方法论:
1. **需求澄清**:用 AI 辅助把模糊需求变清晰(让 AI 反问、列边界);
2. **写 Spec**:输出明确的功能/接口/验收标准(SDD);
3. **规划**:让 AI 拆任务,出 Plan/Todo;
4. **实现**:Agentic 模式分步实现,小步快跑;
5. **验证**:让 AI 跑测试 / 写测试,对照 spec 验收;
6. **Review**:人工 review 关键逻辑、安全;
7. **迭代**:发现问题让 AI 修复,直到通过。
- **体现的认知**:
  - 人负责:需求、架构、验收、把关;
  - AI 负责:实现、测试、重复劳动;
  - **小步快跑 + 持续验证**,而不是"一次性大生成"。
- **加分**:量化提效(时间/质量),讲清边界(哪些必须人做)。

### Q14.8【中】AI 生成的代码你如何 Review?重点看什么?

**考察点:** AI 代码的质量把关能力。

**参考答案要点:**
- **AI 代码的典型问题**:
  - **幻觉 API**:用了不存在的函数/库(最常见!);
  - **过时用法**:库版本旧的写法;
  - **边界遗漏**:异常处理、空值、并发;
  - **安全风险**:硬编码密钥、SQL 注入、未校验输入;
  - **过度设计**:AI 倾向生成"看似完整但冗余"的代码;
  - **逻辑错误**:表面合理但细节错。
- **Review 重点**:
  - **验证 API 真实性**:不熟的 API 查文档;
  - **跑测试**:测试是验证 AI 代码最可靠的方式;
  - **关注边界 / 异常 / 安全**;
  - **对照 Spec 验收**;
  - **静态检查**:lint、类型、安全扫描。
- **原则**:把 AI 代码当"初级工程师的 PR"对待,走同样的质量门禁。

### Q14.9【中】Context(规则文件/文档)工程在 AI 工作流里怎么用?

**考察点:** 让 AI 稳定产出高质量代码的关键 —— 喂对上下文。

**参考答案要点:**
- **问题**:AI 不了解项目约定(代码风格、架构、技术栈) → 产出不符合项目规范。
- **Context 工程手段**:
  - **项目规则文件**:`CLAUDE.md` / `AGENTS.md` / `.cursorrules` / `CONVENTIONS.md`,放项目约定、技术栈、禁忌;
  - **显式 @ 引用**:@file / @symbol 精准注入相关代码;
  - **文档喂入**:API 文档、设计文档、历史决策;
  - **示例引导**:给符合规范的代码示例。
- **价值**:
  - 让 AI"懂项目",产出符合约定;
  - 减少反复纠正;
  - 团队规范一次定义,全员(含 AI)遵守。
- **关键认知**:**规则文件是项目的"AI 接口"**,把隐性知识显性化。

### Q14.10【中高】怎么评估自己的 AI 工作流好不好?有没有量化方式?

**考察点:** 是否有提效度量的意识。

**参考答案要点:**
- **量化维度**:
  - **效率**:任务耗时对比(同样任务 AI 前后);
  - **质量**:bug 率、返工率、测试覆盖率;
  - **采纳率**:AI 生成代码保留比例(改多少);
  - **成本**:token 花费 vs 节省的人力。
- **主观维度**:
  - 认知负荷降低(是否更轻松);
  - 能做以前做不了的事(能力扩展);
  - 学习曲线(新技术上手变快)。
- **务实做法**:记录关键任务的"AI 前 vs AI 后"耗时,长期对比。
- **注意**:不要只看"生成多少代码",要看**交付的业务价值**。

## 第三部分:工具链与生态

### Q14.11【中】你怎么组织自己的 AI 工具链?日常用什么组合?

**考察点:** 是否有体系化的工具栈。

**参考答案要点:**
- **分层工具栈**:
  - **日常编码**:Cursor / 通义灵码(IDE 协同);
  - **复杂任务**:Claude Code / Aider(终端 Agent);
  - **快速原型 / 脚本**:直接对话(ChatGPT/Claude);
  - **知识 / 文档**:AI 搜索(Perplexity)、代码库问答;
  - **自动化 / CI**:把 Agent 接入流水线(批量任务)。
- **配套**:
  - 规则文件(项目约定);
  - Skills(复用 SOP);
  - Prompt 库(常用模板)。
- **原则**:不同任务用不同工具,而非一个工具打天下;**组合 > 单一**。

### Q14.12【高·开放】你如何看待"Prompt 工程"和"代码工程"在 AI 时代的关系?

**考察点:** 深度思考能力(常作压轴开放题)。

**参考答案要点(开放式,有观点即可):**
- **融合趋势**:Prompt 和代码的边界在模糊 —— Prompt 越来越像"声明式编程"(描述要什么),代码是"命令式"(怎么做)。
- **类比**:
  - Prompt 像需求/spec,代码像实现;
  - Skills 像函数,Prompt 模板像 API;
  - 规则文件像配置/契约。
- **核心观点**:
  - **"编程"的本质在扩展**:从写机器指令 → 高级语言 → 框架 → 现在用自然语言"指挥 AI";
  - 但**工程化思维不变**:抽象、复用、测试、版本管理、可维护 —— 这些迁移到 Prompt/Skill 工程;
  - 未来工程师要**双修**:既要会写代码(理解底层),又要会"写 Prompt/搭 Agent"(指挥 AI)。
- **关键认知**:AI 时代,代码量不是价值,**解决问题的能力才是**;Prompt 是新的"编程语言",但工程素养仍是根基。
