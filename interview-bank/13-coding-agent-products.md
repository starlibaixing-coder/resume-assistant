# 模块 13:Coding Agent 与产品架构

> **优先级:🔥 必问**　**覆盖 JD:JD4(核心)/ 全员(产品视野)**
> 这是当前最热的方向。面试官想知道:**你是否真的理解主流 Coding Agent 是怎么设计的,而不只是会用**。会拆解产品 = 有产品思维 + 系统设计能力。

## 知识地图:Coding Agent 的设计维度

```
1. 产品形态分类
   ├─ Chat 助手型    (Copilot Chat: 人主导,AI 辅助回答)
   ├─ IDE 协同型     (Cursor/Cline: 人主导,AI 在编辑器内协同)
   ├─ 终端 Agent 型  (Claude Code/Aider: AI 主导工具调用,人在 CLI 监督)
   └─ 自主 Agent 型  (Devin: 给目标,AI 全程自主完成)
2. 核心能力拆解
   ├─ 代码理解 (AST/CFG/索引,见模块 07)
   ├─ 上下文管理 (代码库检索 / Context Window 管理)
   ├─ 工具调用 (文件读写 / 执行命令 / 测试 / 搜索)
   ├─ 执行循环 (Agentic loop / Plan-Act-Observe)
   └─ 安全边界 (权限 / 沙箱 / Human-in-the-loop)
3. 架构关键点
   ├─ CLI vs Desktop vs Cloud
   ├─ Subagent / 并行
   └─ Checkpoint / 可恢复
```

## 第一部分:产品形态与选型

### Q13.1【高·必问】Copilot、Cursor、Claude Code、Devin 这几类 Coding 工具有什么本质区别?

**考察点:** 是否理解不同产品形态的定位差异(JD4/全员产品视野)。

**参考答案要点:**
按**自主程度(Autonomy)**和**交互位置**分类:

| 类型 | 代表 | 自主程度 | 人机分工 | 典型场景 |
|---|---|---|---|---|
| **Chat 助手** | Copilot Chat | 低 | 人主导,AI 回答问答、生成片段 | 问问题、生成小片段 |
| **IDE 协同** | Cursor / Cline / 通义灵码 | 中 | 人主导,AI 在编辑器内修改代码,人实时 review | 写 feature、重构、补全 |
| **终端 Agent** | Claude Code / Aider | 中高 | AI 主导(可调工具/跑命令),人在 CLI 监督、可打断 | 多文件改动、跑测试、git 操作 |
| **自主 Agent** | Devin / SWE-agent | 高 | 给目标,AI 自主完成全流程(规划/编码/测试/部署) | 端到端完成一个 issue |

- **本质区别**:
  - **自主程度递增** → 效率提升,但可控性下降、风险上升;
  - **交互位置**:IDE 内(所见即所得)vs CLI(命令式)vs Cloud(异步);
  - **工具权限**:从"只改代码"到"能执行任意命令/访问网络"。
- **趋势**:从 Copilot(辅助)→ Cursor(协同)→ Claude Code(agentic)→ Devin(autonomous),自主度越来越高。

**追问方向:** 为什么 Devin 这类自主 Agent 目前还难以完全替代人?(见 Q13.2 长任务的可靠性)

### Q13.2【高·系统设计】像 Claude Code 这样的终端 Agent,架构上是怎么设计的?

**考察点:** 拆解主流产品的能力(JD4 核心)。

**参考答案要点:**
- **核心循环(Agentic Loop)**:
  ```
  用户指令 → LLM 规划下一步 → 调用工具(读文件/改代码/跑命令) 
       → 观察工具输出 → 反思 → 继续直到完成
  ```
  本质是 ReAct/Plan-Act-Observe 循环(见模块 01/02)。
- **关键设计点**:
  - **工具集**:文件读写、bash 执行、代码搜索(grep/AST)、git 操作、网络请求、子 Agent 调度;
  - **上下文管理**:这是核心难点——大代码库不能全塞,靠**精准检索**(grep/AST/语义)+ **token 预算管理**(见 Q02.2);
  - **权限与安全**:危险操作(删文件、执行任意命令)需用户确认(Human-in-the-loop),沙箱隔离;
  - **可恢复**:checkpoint/会话持久化,任务可中断恢复;
  - **Subagent**:把大任务派发给子 Agent 并行处理(见模块 14)。
- **为什么是 CLI 而不是纯 IDE**:
  - CLI 天然能执行任意命令、跑测试、操作 git,工具能力强;
  - 适合"多步骤、多文件、需执行"的复杂任务;
  - 与开发者既有工作流(终端)融合。
- **核心挑战**:① 上下文管理(代码库大);② 长任务可靠性(见 Q09.6);③ 工具调用准确率;④ 成本控制。

**追问方向:** Claude Code 怎么决定读哪些文件?(grep 关键词 → 看目录结构 → 按需读 → AST 找依赖)

### Q13.3【中高·必问】Desktop、CLI、Cloud 三种 Agent 形态怎么选?各有什么优劣?

**考察点:** 产品形态的工程选型判断。

**参考答案要点:**
按**运行位置**和**适用场景**对比:

| 形态 | 代表 | 运行位置 | 优势 | 劣势 | 适用 |
|---|---|---|---|---|---|
| **Desktop(桌面 GUI)** | Cursor / Cline | 本地 IDE 内 | 可视化、所见即所得、实时 review、体验好 | 受限于 IDE 生态、难做长任务 | 日常编码、feature 开发 |
| **CLI(命令行)** | Claude Code / Aider | 本地终端 | 工具能力强(任意命令/git)、可脚本化、与终端工作流融合、适合自动化 | 无 GUI、上手门槛、review 不直观 | 多文件改动、CI 集成、自动化任务 |
| **Cloud(云端异步)** | Devin / Factory | 云端虚拟机 | 全自主、可长时间运行、不占本地资源、可并行多任务 | 不可控、延迟高、安全敏感(代码上云)、成本高 | 端到端 issue、批量任务、需要完整环境 |

- **选型原则**:
  - **要可视化、实时把控** → Desktop(IDE);
  - **要强工具能力、自动化、CI 集成** → CLI;
  - **要全自主、长时间任务、批量** → Cloud;
  - **安全敏感(代码不能上云)** → 本地(Desktop/CLI);
  - **生产实操主流**:Cursor(日常)+ Claude Code(复杂/自动化)组合。

**追问方向:** 为什么企业级场景对 Cloud Agent 有顾虑?(代码安全、数据合规、可控性)

### Q13.4【中】做 Coding Agent,代码库太大塞不进 context,怎么解决?

**考察点:** 代码 Agent 的核心难题(连接模块 07)。

**参考答案要点:**
- **不全塞,按需检索加载**:
  - **文件树概览**:先看目录结构,建立整体认知;
  - **关键词检索**(ripgrep):定位相关文件;
  - **符号检索**(AST/LSP):找定义、引用、调用关系;
  - **语义检索**(embedding):用自然语言找代码;
  - **Lazy 加载**:只读当前需要的,细节按需展开。
- **上下文组装**:检索到的相关代码 + 调用链 + 类型信息,按 token 预算裁剪。
- **记忆机制**:跨步骤记住已探索的结构,避免重复检索。
- **核心矛盾**:检索 recall(不漏)vs context 预算(不爆),需平衡。
- **详见模块 07 的代码库理解方案(Q07.1)。**

## 第二部分:产品架构深度

### Q13.5【高】Cursor 的 Composer / Agent 模式和普通 Chat 补全有什么区别?

**考察点:** 理解 IDE Agent 的演进。

**参考答案要点:**
- **普通补全**(Tab 补全):单点预测下一行,人主导,AI 补全;
- **Chat**:问答式,生成片段,人手动应用;
- **Composer/Agent 模式**:
  - **多文件协同编辑**:能同时修改多个文件,理解跨文件依赖;
  - **Agent 模式**:能自主执行(读文件、跑命令、看错误、迭代修复),形成 agentic loop;
  - **上下文管理**:@file / @codebase 显式注入,或自动检索 codebase;
  - **Apply 机制**:AI 生成 diff,人 review 后一键应用。
- **本质演进**:从"补全工具"→"协同编辑器"→"Agent"。

### Q13.6【高·系统设计】如果要你设计一个类似 Devin 的自主 Coding Agent,核心要解决哪些问题?

**考察点:** 综合系统设计能力(JD4 高频系统设计题)。

**参考答案要点:**
按子系统拆解:

1. **规划与拆解**:
   - 把"解决这个 issue"拆成可执行子任务(读代码 → 定位 → 改 → 测试 → 提 PR);
   - Plan-and-Execute + 动态重规划。

2. **代码理解**(模块 07):
   - 代码库索引、AST、call graph、语义检索;
   - 解决"大代码库塞不下"。

3. **执行环境**:
   - 云端虚拟机/容器,提供完整开发环境(代码、依赖、终端);
   - 沙箱隔离(爆炸半径可控)。

4. **工具集**:
   - 文件操作、bash、git、测试运行、浏览器(看报错/文档)、搜索;
   - 工具描述清晰,确保调用准确。

5. **自我验证**(关键差异化):
   - 改完**自己跑测试**,看是否通过;
   - 看报错 → 修复 → 再跑,形成闭环;
   - 这是区别"会写代码"和"能交付"的核心。

6. **长任务可靠性**(模块 09/10):
   - checkpoint、断点续跑、预算控制、超时保护;
   - 避免无限循环。

7. **安全边界**:
   - 高危操作(部署、删库)必须 HITL;
   - 最小权限、审计日志。

8. **人机协作**:
   - 关键决策点暂停等人确认;
   - 进度可见、可打断、可回滚。

9. **评测**:用 SWE-bench 等基准评测(issue 解决率)。

- **核心难点**:**可靠性** —— 长链条上任何一步出错都导致整体失败,需要强验证 + 强纠错。

**追问方向:** Devin 为什么难做成?(长链可靠性 + 复杂环境适配 + 成本)

### Q13.5.5【中】SWE-bench 是什么?为什么对 Coding Agent 重要?

**考察点:** Coding Agent 的评测认知。

**参考答案要点:**
- **SWE-bench**:从真实 GitHub 仓库(Python 项目)收集的 issue + 对应 PR + 测试,作为 Coding Agent 的基准评测。
- **任务**:给 Agent 一个 issue,让它改代码并通过测试;
- **指标**:解决率(passed@k)—— 多少 issue 能正确解决。
- **意义**:
  - 是目前 Coding Agent 最权威的实战评测(非人造任务);
  - 直接反映 Agent 的"端到端交付能力";
  - 各家(Claude/GPT/Devin)都刷这个榜。
- **局限**:覆盖偏 Python、测试覆盖度影响结果、不评估代码质量(只看测试通过)。

### Q13.7【中】为什么 Coding Agent 强调"跑测试/看报错"这个闭环?不能一次写对吗?

**考察点:** 理解 Agent 自我验证的价值。

**参考答案要点:**
- **一次写对很难**:代码涉及多文件依赖、API 细节、边界,LLM 很难一次全对;
- **闭环的价值**:
  - **环境反馈是最真实的 ground truth**——编译错、测试失败、运行异常比 LLM 自评可靠得多;
  - 形成写 → 跑 → 看错 → 改的迭代循环,逐步收敛;
  - 类似人类开发的 TDD/迭代过程。
- **关键认知**:Agent 的优势不是"一次写对",而是**"能快速迭代到对"**——把人类来回调试的过程自动化。
- **工程意义**:给 Agent 配测试工具 + 允许它多轮迭代,比追求"一次生成"更现实、效果更好。

### Q13.8【高】Coding Agent 会不会完全替代程序员?你怎么看它的能力边界?

**考察点:** 对技术趋势的判断力(常作为开放题)。

**参考答案要点:**
- **短期不会完全替代**,能力边界明显:
  - **架构决策 / 技术选型**:需要业务理解、trade-off 判断,AI 难替代;
  - **需求澄清 / 模糊问题定义**:把模糊需求变清晰是人的核心价值;
  - **跨团队协作 / 沟通**:人际、政治、商业判断;
  - **责任与决策**:出了问题谁负责,需要人兜底;
  - **创新 / 从 0 到 1**:AI 擅长模式内的工作,突破性创新弱。
- **AI 擅长的**:
  - 明确任务的实现、重复劳动、测试生成、文档、重构、bug 修复;
  - 已有范式内的编码。
- **趋势判断**:
  - AI 不会替代程序员,但**会用 AI 的程序员会替代不会用的**;
  - 程序员价值上移:从"写代码"→"定义问题、设计架构、把关质量、驱动业务";
  - 单人产出放大,团队规模可能缩小,但不是消失。
- **(展开见模块 15 的程序员定位讨论)**
