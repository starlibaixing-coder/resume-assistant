### 题目

### Q11.1【中】给你 100 万条向量，用户每次 query 要返回最相似的 top-10，怎么做？暴力算行不行？

**考察点：** ANN 检索（RAG 生产必考）。

**参考答案要点：**
- **暴力 KNN**：O(N×D)，百万级撑不住（每次 query 几秒到几十秒）。
- **ANN（近似最近邻）**：牺牲一点精度换速度。
  - **HNSW**（Hierarchical Navigable Small World）：图索引，查询快（毫秒级）、精度高，但费内存、构建慢。
  - **IVF**（Inverted File）：聚类后只搜最近的几个簇，速度快、省内存，精度略低。
  - **PQ**（Product Quantization）：乘积量化压缩向量，省内存，常和 IVF 组合（IVF-PQ）。
- **生产实践**：百万级常用 HNSW 或 IVF + PQ；再加 rerank 精排提精度。
- **trade-off**：召回率 vs 延迟 vs 内存，按业务调参。

**追问方向：** HNSW 的 efSearch / M 参数怎么调？（M 影响图的连接度，efSearch 影响搜索范围）

### Q11.2【中】为什么向量检索要 normalize？余弦相似度和点积什么关系？

**考察点：** 向量检索基础。

**参考答案要点：**
- **归一化后**，向量长度为 1，**余弦相似度 = 点积**。可以用更快的点积计算。
- **为什么归一化**：
  - 消除向量长度差异，只比方向（语义），不被长文档"长度"干扰；
  - 点积计算更快（很多向量库优化）；
  - 不同 embedding 模型的输出尺度不同，归一化统一。
- **余弦 vs 欧式**：归一化后二者等价（单调对应）；余弦对长度不敏感，更适合文本语义。

### Q11.3【高】一个 Agent 有 50 个子任务，存在依赖关系（A 完成才能做 B），怎么调度？怎么并行最大化？

**考察点：** DAG + 拓扑排序 + 并行调度（LangGraph 这类框架的内核）。

**参考答案要点：**
- **建模**：把子任务建成 DAG（有向无环图），边表示依赖。
- **拓扑排序**：确定执行顺序，无依赖冲突。
- **并行最大化**：
  - 同一时刻，所有"前置依赖均已完成"的节点可并行执行；
  - 每轮取入度为 0 的节点全部并行跑（类似 Kahn 算法分层）；
  - 受限于资源上限（并发数 / token 预算），用线程池 / 异步调度。
- **容错**：节点失败 → 重试 / 跳过 / 回退；记录状态，支持续跑（对应 Q09.6）。
- **检测环**：拓扑排序能检测依赖环（环 = 死锁，需避免）。

**追问方向：** 如果是动态依赖（执行中才知道下一步）怎么办？（运行时按结果决定后继，类似 ReAct）

### Q11.4【中】LRU 缓存怎么实现？在 Agent 里用在哪？

**考察点：** 经典数据结构 + Agent 落地。

**参考答案要点：**
- **实现**：HashMap + 双向链表，O(1) get/put。
  - HashMap 存 key→node，O(1) 查找；
  - 双向链表维护访问顺序，访问即移到头，满时删尾。
- **Agent 应用**：
  - **对话历史淘汰**（有限 context 保留最近 / 最有价值的历史）；
  - **LLM 响应缓存**（相同 prompt 命中）；
  - **工具结果缓存**；
  - **KV Cache 淘汰**（推理引擎内部）。

### Q11.5【中·手撕】实现一个滑动窗口，用于截断对话历史，保留最近 N 轮 + 永久保留 system prompt。

**考察点：** 基础编码 + 理解上下文管理。

**参考答案要点（伪代码思路）：**
- 维护 history 列表 + system prompt（单独存储，不进窗口）；
- 每次构造请求时：取 history 的后 N 轮；
- 若总 token 超限，继续从最老的开始剔除，直到满足；
- 进阶：被剔除的内容可触发摘要压缩（rolling summary），摘要常驻。
- 边界：单轮就超限的处理（截断该轮或报错）。

### Q11.6【高】2GB 的日志文件，RAG 切块时怎么平衡"块太大塞不下"和"块太小丢上下文"？

**考察点：** chunking 策略（RAG 核心）。

**参考答案要点：**
- **基础策略**：固定大小（如 500 token）+ overlap（如 50 token），保证边界信息不丢。
- **语义边界切块**：按段落 / 句子 / 标题切，避免切断完整语义。
- **Parent-Child**：
  - 切小 chunk 用于检索（精准）；
  - 每个小 chunk 关联一个更大的 parent chunk，命中时返回 parent（保上下文）。
- **结构感知**：日志类可按时间窗口 / 请求 ID 切，保留事件完整性。
- **MapReduce**：超长文档先分块摘要，再汇总摘要（两阶段）。
- **评测驱动**：不同切法跑评测集对比，选最优。

## 第二部分：设计模式 → Agent 落地

### 知识对照表（金矿：能把设计模式与 Agent 架构对应，直接体现工程素养）

| 设计模式 | 在 Agent 中的真实应用 |
|---|---|
| **策略模式 (Strategy)** | 切换 Planning 策略（ReAct / Plan-Execute）、不同检索策略、模型路由策略 |
| **责任链 (Chain of Responsibility)** | Guardrails 处理链：输入校验→敏感词→注入检测→LLM→输出审核 |
| **装饰器 (Decorator)** | 给 LLM 调用叠加：日志 / 缓存 / 重试 / 限流 / trace / metrics |
| **工厂模式 (Factory)** | 按配置创建不同 Agent / Tool / 模型客户端 |
| **观察者 / 发布订阅** | Agent 事件流：每步发事件 → 日志 / 监控 / UI 流式更新订阅 |
| **状态机 (State Machine)** | LangGraph 本质；Agent 状态流转（空闲→规划→执行→等待→结束） |
| **模板方法 (Template Method)** | Agent 执行骨架（prepare→plan→act→observe→reflect）固定，子类填实现 |
| **代理模式 (Proxy)** | Tool 代理封装（加权限 / 缓存 / 日志）、远程模型代理 |
| **单例 (Singleton)** | 模型客户端、向量库连接池、配置中心 |
| **适配器 (Adapter)** | 统一不同 LLM provider 接口（OpenAI / Claude / Qwen） |
| **建造者 (Builder)** | 复杂 Prompt 构建（多段拼接）、Agent 配置构建 |

### 题目

### Q11.7【高·必问】设计一个支持多模型（GPT/Claude/Qwen）、可切换、可加监控的 LLM 调用层，用什么设计模式？

**考察点：** 综合设计能力——答出来工程素养直接拉满。

**参考答案要点（组合拳）：**
- **适配器模式**：定义统一抽象 `LLMClient.chat()`，各 provider 写适配器实现（抹平接口差异）。
- **工厂模式**：按配置 / 策略创建对应的 client 实例。
- **装饰器模式**：在 `chat()` 外面包 `@retry @cache @log @trace @metrics`，横切关注点与核心逻辑分离。
- **策略模式**：运行时按任务选择模型路由策略（成本优先 / 质量优先 / 降级链）。
- **价值**：新增 provider 只加一个适配器；加监控不改核心代码；切换模型一行配置。

**追问方向：** 装饰器在 Python 里怎么实现？（函数装饰器 / 类装饰器；注意保持签名与异步兼容）

### Q11.8【中】流式输出（streaming）用哪个设计模式实现最自然？

**考察点：** 观察者模式的识别。

**参考答案要点：**
- **观察者 / 发布订阅**：LLM 产出 token → 推送给所有订阅者（前端 SSE、日志、metrics、转写）。
- **也可用迭代器 / 生成器**（Python async generator）：`async for chunk in stream()`。
- **解耦**：生产者（模型）不关心有多少消费者，消费者按需订阅。
- **LangChain 的 Callbacks** 就是观察者模式的实现。

### Q11.9【中高】用责任链模式设计一套 Agent 输入输出的安全中间件。

**考察点：** 安全工程 + 设计模式结合（对应 Q10.7 Prompt 注入防御）。

**参考答案要点：**
- **链式结构**，每个 handler 决定放行或拦截：
  ```
  InputSanitizer → PromptInjectionDetector → PIIMasker
       → LLMCall → OutputFilter → ContentModerator
  ```
- **特点**：
  - 顺序执行，任一环节拦截即终止；
  - 每个 handler 单一职责，可独立测试；
  - 可配置、可插拔（按场景增减 handler）；
  - 易扩展（新增检查只加一个 handler）。
- **落地**：Python 可用函数链 / 类继承；Web 框架中间件本质就是责任链。

### Q11.10【高】LangGraph 为什么要用图 / 状态机模型，而不是普通的函数调用链？

**考察点：** 对 Agent 编排本质的理解。

**参考答案要点：**
- **普通函数链的局限**：线性、无状态、难循环、难中断恢复。
- **状态机 / 图解决**：
  - **循环**：ReAct 的 act-observe 反复执行；
  - **条件分支**：按结果动态决定下一步（成功→继续，失败→重试 / 回退）；
  - **断点恢复**：checkpoint + 状态持久化（长任务续跑）；
  - **并行**：分支并行执行后汇总；
  - **human-in-loop**：某节点暂停等人工确认。
- **本质**：Agent 的执行是**带状态的非线性流程**，状态机是最自然的建模方式。函数链只能表达"配方"，状态机能表达"流程"。
