# 刷题站 Agent 化设计(Tauri + LLM)

- **日期**:2026-08-13
- **范围**:`quiz-app/` 从纯前端静态站演进为 Tauri 桌面 LLM Agent
- **目标**:在不破坏现有刷题核心的前提下,把 LLM 能力(生题/改删/简历/JD 定向/模拟面试)以 agent 形态集成进桌面应用,并保留 web 版作为只读传播入口。
- **状态**:✅ 设计已锁定(经 grill-me 8 轮访谈磨砺),待施工
- **产出方式**:grill-me 访谈(一问一答式磨砺,含一次设计反转,见 §5)

---

## §1 背景与动机

现有 `quiz-app/` 是 **React 19 + Vite + Tailwind v4 + shadcn 的纯前端静态站**,部署在 GitHub Pages。数据源是构建时打进 bundle 的 `questions.json`(由 `banks/*.yaml` 经 `build.mjs` 生成),用户态只有 localStorage(复习进度 + 笔记)。**没有任何服务端。**

用户提出把 LLM 加进来、做成 agent,初始想法是 6 个功能:① 知识点生成题 ② 增加题库类型 ③ 页面制作简历 ④ 分析 JD+简历生成定向题 ⑤ 模拟面试 ⑥ 改删已有题。

这 6 个想法里有 5 个绕不开两堵墙:**调 LLM(要 API key)** 和 **存用户数据(要持久化)**。静态站两堵墙都过不去。本设计通过 grill-me 访谈逐层磨砺,最终落定为 Tauri 桌面应用形态。

---

## §2 设计总览

**一句话架构**:Tauri 桌面壳里跑 React 前端(复用现有刷题核心)+ JS agent 编排(Vercel AI SDK / LangChain.js),Rust 侧只提供系统能力(文件、secure store、Chrome 渲染)作为工具;官方 YAML 题库只读共享,用户生成的题落本地 SQLite;web 版冻结为只读快照负责传播。

| 维度 | 决策 |
|---|---|
| **形态** | Tauri 桌面端(主,AI 重能力)+ web 静态站(只读刷题快照,传播) |
| **受众** | 自用为主,顺带分享 |
| **数据** | 官方 YAML 库(只读、git、两端共享)+ 本地"我的库"(SQLite,双库并列聚合) |
| **中枢** | 求职目标档案(简历+JD+公司+偏好)app 一等公民,功能 ③④⑤ 围绕它 |
| **编排** | 前端 JS(Vercel AI SDK / LangChain.js);Rust 只做系统能力工具,复用 `skill/` |

## §3 关键决策(ADR)

每条决策记录上下文 / 决策 / 理由 / 后果 / 状态。施工时若想推翻某条,先读本节对应 ADR 的理由。

### ADR-1 形态:Tauri 桌面端 + web 只读快照双轨

- **决策**:Tauri 桌面端为主形态(跑 AI 重能力),现有 web 站冻结为只读刷题快照(负责传播)。
- **上下文**:LLM 调用要 API key,静态站无处安全放 key;用户数据要持久化,localStorage 换设备即丢。
- **理由**:Tauri 同时绕过 key 墙(本地 secure store)和数据墙(本地文件/SQLite),还能复用 `skill/` 渲染生态;web 的传播价值仍保留(链接即开即用)。
- **后果**:现有 GitHub Pages 部署/CI/base 路径那套对 web 仍保留;Tauri 是新增的主开发线。
- **状态**:✅ 已接受

### ADR-2 受众:自用为主,顺带分享

- **决策**:产品定位为自用工具,顺带可分享给朋友/同学。
- **上下文**:受众决定 Tauri(桌面、本地、强能力)是否比后端 BFF(web 主形态、可公开分发)更合适。
- **理由**:自用场景下 Tauri 的本地安全/持久化/复用 skill 优势压倒 web 的传播优势。若未来转向公开产品,应重评此条(见 §6 风险)。
- **后果**:不投入做公开分发所需的账号体系/服务端/托管;接受"分享"主要靠 web 只读快照。
- **状态**:✅ 已接受

### ADR-3 数据:官方库 + 我的库,双库并列聚合

- **决策**:官方 YAML 库只读不动(`questions.json`),本地"我的库"独立存储,刷题界面聚合两者。官方题不可原地改删;功能 ⑥"改删已有题"仅对"我的库"生效,对官方题只能"复制成副本再改"。
- **上下文**:用户在页面增删改题,与 AGENTS.md 第一条"YAML 是源,不要手改 questions.json"正面冲突。
- **理由**:双库并列保护官方库的 git 可追溯 + review 体系完整,同时给用户生成的题独立的落位。
- **后果**:要写聚合加载逻辑;官方题的"改"语义重定义为"复制后改"。
- **状态**:✅ 已接受

### ADR-4 中枢:求职目标档案为一等公民

- **决策**:建"求职目标"档案(我的简历 + 目标 JD + 目标公司 + 偏好),作为 app 一等公民持久化,功能 ③(简历)/④(JD 定向生题)/⑤(模拟面试)都读它。
- **上下文**:③④⑤ 三个功能共享同一份"简历+JD+公司"上下文。
- **理由**:把孤立工具升级为围绕一个目标的多步工作流,这才是"agent"的核心价值,而非套壳工具集。
- **后果**:要先设计档案结构与录入/编辑界面;功能间产生耦合(改简历后面试官立即可见)。
- **状态**:✅ 已接受

### ADR-5 编排:前端 JS 大脑 + Rust 系统能力工具

- **决策**:agent 多步规划/工具调用/LLM 流式都在前端 JS(Vercel AI SDK 或 LangChain.js);Rust 只暴露系统能力(文件读写、secure store、调 Chrome 渲染 PDF)作为 Tauri command。
- **上下文**:Tauri 的 agent 大脑放 Rust 还是 JS,决定能否复用 JS 生态与现有 `skill/`。
- **理由**:① JS LLM agent 生态成熟,远超 Rust(rig 等);② 用户栈是 JS/TS,`skill/render-pdf.mjs` 是 ESM JS,放 JS 侧能平滑复用;③ R1/R2/R3 红线写在 `skill/SKILL.md`,JS 侧能直接当 system prompt 用。
- **后果**:key 经 Tauri command 注入前端,安全性略低于纯 Rust 侧调用,但对自用工具足够(secure store 已远好于纯 web)。
- **状态**:✅ 已接受

### ADR-6 代码共享:冻结 web,Tauri 独立演进

- **决策**:web 版冻结在当前 commit(只读刷题快照,不再演进);Tauri 版从 `quiz-app/` 复制一份起头,独立大改(换 SQLite / 加 AI 层)。两份代码不强行共享。
- **上下文**:现有 quiz-app 为 GitHub Pages 配了 `BASE_URL` / hash 路由 / localStorage / fetch questions.json,迁 Tauri 要大改。
- **理由**:web 已完整且定位只读、不再演进;硬做"一套代码两个壳"会让 Tauri 版背上兼容 web 的条件分支包袱。
- **后果**:官方库更新时 web 要重建 questions.json 重新部署(现有 CI 保留);Tauri 版独立迭代,不背 web 兼容债。
- **状态**:✅ 已接受

### ADR-7 我的库格式:SQLite(经反转,见 §5)

- **决策**:"我的库"用 SQLite 存 `app_data_dir`,多表(题目 / 进度 / 笔记 / 档案)关系完整 + 事务安全;配 app 层导出/导入做备份(导出支持 YAML 格式,留"好题贡献回官方库"的接口)。
- **上下文**:双库模型下"我的库"用什么格式存,是 ADR-9(SM-2 跨库)和 ADR-10(质量闸)的地基。
- **理由**:本应用本质是 Anki 类 SM-2 桌面题库,SQLite 是事实标准范式(Anki 先例);多表关系 + 事务安全原生支持。(最初考虑 YAML,被反转,详见 §5。)
- **后果**:校验规则需从 `audit.mjs` 抽成与格式无关的共享函数;备份走 app 导出,不走 git。
- **状态**:✅ 已接受(反转后)

### ADR-8 key/provider:secure store + OpenAI 兼容抽象

- **决策**:key 用户自填,存 Tauri secure store(系统 keychain),运行时注入;provider 做 OpenAI 兼容抽象层,优先适配智谱(用户在用 GLM),顺带覆盖 DeepSeek / 月之暗面等国产模型 + 本地 Ollama(离线零成本)。
- **上下文**:LLM key 不能内置、不能经开发者服务器;provider 范围决定适配工作量。
- **理由**:OpenAI 兼容协议一套抽象覆盖大半国产模型,Ollama 也提供兼容端点等于免费送离线选项;key 自填保持纯本地、零成本、零运维。
- **后果**:非 OpenAI 兼容的(如 Anthropic 原生格式)要单独适配,初版可不做。
- **状态**:✅ 已接受

### ADR-8b 受众多层:朋友走 web 免 key,AI 留自用

- **决策**:接受"key 自填"对分享受众的天然门槛——不懂技术的朋友用 web 版只读刷题(无需 key),Tauri 版 AI 留给自用 + 懂技术的人。
- **上下文**:"key 自填"(ADR-8)和"顺带分享"(ADR-2)合在一起有个未显化的冲突:不懂技术的朋友搞不到 key。
- **理由**:为消除门槛做代理后端会回到最初否掉的 BFF 路线,违背纯本地初衷;天然分层符合"自用为主"定位。
- **后果**:朋友享受不到 AI 功能;若未来想让朋友也能用 AI,需重评此条(见 §6 风险)。
- **状态**:✅ 已接受

### ADR-9 SM-2 跨库:统一进度表 + id 跨库唯一 + 官方 id 不可变

- **决策**:进度统一存 SQLite 一张 `review_state(id, ...)` 表,官方题与我的题的进度都进这张表;id 跨库全局唯一(我的库用 `my-*` 或用户自定义 slug,避开官方 slug);**官方库 id 立为"一旦发布永久锁定"的不可变约定**。
- **上下文**:双库聚合后,进度 key 必须跨库唯一;官方库会持续迭代,若 id 变动会让用户复习进度悬空。
- **理由**:id 唯一 ≠ id 稳定。用户在官方题 `agent.01.1` 上复习数月,若题库更新时该 id 消失/重排,进度即丢。锁定官方 id 是保护用户数据的唯一可靠手段。
- **后果**:`build.mjs` 要加校验:对比历史 `questions.json` 的 id 集合,官方 id 消失或改动即报错;维护题库时改题只能改内容不能改 id,删题则 id 作废不复用。
- **状态**:✅ 已接受

### ADR-10 质量闸:草稿区 + approve 全链路

- **决策**:AI 生成走全链路——prompt 内嵌 QUALITY.md 规则 → 预检跑共享校验函数(不达标让 AI 自修正重试 N 次)→ 进"草稿区"(pending)→ 用户 approve 后才入正式库 + 进 SM-2 队列。硬规则(answer≥50字 / difficulty / id 唯一)程序判;语义规则(答案泄漏 / focus 泄漏 / 概念层次)LLM 自查 + 人审。
- **上下文**:AI 生成题若直接进复习队列,垃圾题会污染 SM-2 调度;且 AI 是质检高危区(倾向泄漏答案、概念层次混乱、answer 凑字数)。
- **理由**:延续 QUALITY.md 信仰 + R3(候选线索必须用户确认)精神;草稿区 approve 保证库永远干净,且自用场景下审题本身即学习。
- **后果**:多一步 approve;预检/自修正增加 token 成本;需实现草稿区 UI 与状态。
- **状态**:✅ 已接受

## §5 设计反转记录:#2 存储格式 YAML → SQLite

本设计在访谈中被用户反过来 grill 过一次,记录于此,防止未来有人用同样错误论据翻回 YAML。

**最初倾向**:"我的库"用 YAML,三个理由:① 可 git 同步备份;② 和官方库同构(同一心智模型);③ `audit.mjs` 校验可直接复用。

**用户反问**:"这已经是 Tauri 应用了,它存的东西只和应用有关,为什么会涉及 git?"

**三个论据逐个失效**:
1. **git 备份** —— 错。Tauri 应用数据是运行时私有数据(存 `app_data_dir`),不是源码,不进 git 仓库。把"官方 YAML 库在 git 里"外推到"我的库也该靠 git",**混淆了源码与运行时数据**。
2. **和官方库同构** —— 无所谓。双库本就并列独立、聚合展示,我的库没必要和官方库同构。
3. **audit.mjs 校验复用** —— 站不住。audit.mjs 校验的是源库**文件结构**(扫 `banks/*.yaml`、id 三段式依赖仓库目录),运行时我的库套不上;真正要的是**运行时校验规则**,应从 audit.mjs 抽成与格式无关的共享函数。

**重新评估**:本应用本质是 Anki 类 SM-2 桌面题库,数据是多类有关系的(题目↔进度↔笔记↔档案)、要事务安全。SQLite 是桌面应用事实标准范式(Anki 先例)。**结论反转为 SQLite。**

**教训**:别用"官方库怎么存"去锚定"应用运行时数据怎么存"——两个世界。备份走 app 层导出/导入,不是 git。

## §6 MVP 与路线图

**MVP 原则**:用最小切法打穿最致命的假设——"LLM 能在本地带 key、把生成内容落进可持久化的库、再被刷题和 SM-2 消费"这条线真的跑得通。

| 阶段 | 内容 | 验证目标 |
|---|---|---|
| **阶段 0(地基)** | Tauri 壳初始化、刷题站迁入、SQLite 双库骨架、secure store、JS 编排骨架、provider 抽象 | 桌面壳能跑、刷题核心不退化 |
| **阶段 1(MVP)** | 功能 ①(知识点生题)+ 功能 ⑥(改删我的库) | LLM→我的库→刷题→SM-2 整条管线 |
| **阶段 2** | 中枢档案录入 + 功能 ④(JD 定向生题) | 求职目标接进生成 |
| **阶段 3** | 功能 ③(简历,复用 `skill/`) | R1/R2/R3 在桌面 agent 落地 |
| **阶段 4** | 功能 ⑤(模拟面试) | 多轮对话 + 评分反馈 |

**功能 ②(增加题库类型)**:不是独立功能,是数据模型——双库设计里留好"用户自定义分类"即自然支持。原列表把它当功能是认知误区。

### 重评触发条件(风险)

以下变化发生时,需回头重评对应 ADR:
- **若转向公开产品**(受众扩大):重评 ADR-2 / ADR-8b —— 可能需要后端 BFF + 账号体系,Tauri 退为可选。
- **若想让分享受众也用 AI**:重评 ADR-8b —— 需要做带额度的代理后端或引导申请流程,纯本地架构被打破。
- **若官方库 id 历史包袱过重**:重评 ADR-9 —— 可考虑 id 不可变校验降级为警告。

## §7 可执行纪律(施工硬约束)

以下是从各 ADR 提炼的、施工时必须遵守的硬约束(非建议):

1. **`build.mjs` 加 id 不可变校验**:对比历史 `questions.json` 的 id 集合,官方 id 消失或改动即报错(ADR-9)。
2. **AI 生成 prompt 内嵌 QUALITY.md 规则**:生成后预检跑共享校验函数(从 `audit.mjs` 抽出),不达标自修正重试 N 次(ADR-10)。
3. **AI 题一律先进草稿区**:未经 approve 不进 SM-2 队列(ADR-10)。
4. **我的库 id 用 `my-*` 或用户自定义 slug**:避开官方 slug,保证跨库全局唯一(ADR-9)。
5. **存储层抽象接口**(`loadQuestions` / `getProgress` / `saveProgress`):Tauri 实现走 SQLite,为未来兼容留口(ADR-6/7)。
6. **provider 抽象走 OpenAI 兼容协议**:智谱优先、Ollama 本地可选(ADR-8)。
7. **R1/R2/R3 延续**:`skill/SKILL.md` 的三条红线作为简历相关 agent 的 system prompt 约束,功能 ③ 落地时必须接入(ADR-5)。
8. **备份走 app 导出/导入,不走 git**:运行时数据与源码两个世界(§5 教训)。
